## Committing to the Mission

### Why the shipping rails matter more than the card itself

In this build, I shipped a sourced Global-Problem Card through a full GitHub delivery loop. The work covered planning, drafting, scoring, branching, pull request review, merge, and release tagging.

The card mattered, but the larger value was the rail system around it. I was learning how to move an idea through a professional version-control workflow with issues, acceptance criteria, rubric checks, and a clean release.

This mattered because software delivery is not only about creating an artifact. It is about proving how the artifact moved from planned work to finished work with a trail that someone else can inspect.

## Setting Up the Engineering Environment

### Purpose of the setup step

In this step, I set up the development environment for the GitHub delivery workflow. I installed Git, the GitHub CLI, and a code editor so I could manage the build from my local machine.

I also configured my GitHub organization so the repository, issues, branches, and release could live inside a professional workspace. That gave the card a proper delivery home instead of leaving it as a local file.

This setup mattered because the workflow needed a working command line before any card work could be trusted. If Git, GitHub authentication, or org access failed, the shipping loop would break before the artifact reached review.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/ee3aae6a-d0f4-444e-8c8f-6b5ee9efe331_w8yi2ngv)

### Day-zero gate: three commands, three confirmations

I ran git --version, gh auth status, and gh org list in the terminal. These commands confirmed that Git was installed, the GitHub CLI was authenticated, and the GitHub organization was linked and accessible.

That day-zero gate gave the build a clear readiness check. It proved the local machine could talk to GitHub before the repository and project workflow were used.

The result was simple but important. The shipping rail was ready before the card draft entered the system.

## Designing Before Building

### Why design precedes execution

In this step, I designed the requirements, decision records, and build plan before writing the final card. The goal was to define acceptance criteria and create a clear path for the work.

This kept the card from becoming a loose writing task. The decision record, rubric, and delivery plan gave the build a standard to meet before anything could be shipped.

Designing first mattered because the final artifact had to satisfy the rubric, not just sound good. The plan made the quality gate explicit before drafting started.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/ee3aae6a-d0f4-444e-8c8f-6b5ee9efe331_xwv5tifc)

### Defending a MADR decision record

I chose the decision about AI drafting. The selected path used Ollama with Gemma 3 instead of manual drafting or a metered AI service.

That decision gave the build zero marginal cost and offline capability. It also kept the drafting path local, which fit the purpose of a repeatable shipping workflow.

The reversal trigger was clear. If the machine lacked the RAM or disk space needed to run Ollama, I would switch to a flat-rate AI client.

## Standing Up the Rails and AI-Drafting the Card

### Repo, board, and issues before a single line of card

In this step, I created the private repository and organized the working structure before drafting the card. The goal was to establish the GitHub loop before content work began.

The repository gave the build version control. The board and issues gave the work a planned path from task to completion.

This mattered because the card needed to move through the same rails every future artifact could use. The process came first, then the draft.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/ee3aae6a-d0f4-444e-8c8f-6b5ee9efe331_1d6i1yqk)

### AI drafts first; rubric scores second

I gave the AI the card template and the sample problem file to create a structured draft. That draft became the first artifact to test against the rubric.

The draft had to exist before scoring because the rubric acted as a quality gate. It gave me a way to judge the AI output against a fixed standard instead of deciding by feel.

This sequence kept the workflow honest. AI could draft, but the rubric decided whether the draft was ready to move forward.

## Scoring the Draft and Enforcing the Quality Gate

### What the rubric-gating step achieves

In this step, I scored the AI-generated draft against the rubric. The goal was to find what needed to be corrected before the card became a release artifact.

The rubric checked whether the content was clear, sourced, and honest. It also forced the honest-limit line to be direct instead of polished around the weakness.

This mattered because AI-generated writing can sound confident while hiding soft claims. The quality gate made the draft earn its way into the release.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/ee3aae6a-d0f4-444e-8c8f-6b5ee9efe331_smzo3vad)

### Where the AI failed and how it was fixed

The AI draft failed rubric item three because it used hedged, diplomatic language. The phrase while this card alone may not fully address the problem softened the honest limit instead of stating it clearly.

I fixed it by removing the conditional phrasing and replacing it with a direct statement: This card does not connect a single offline person.

That change made the limitation binary and fact-based. The card stopped performing humility and stated the constraint plainly.

## Shipping the Card and Closing the Loop

### Branch, PR, merge, release

In this step, I shipped the card through the GitHub workflow. I created a dedicated feature branch, committed the signature artifacts, and pushed the branch to GitHub.

The pull request moved the work into review and gave the repository a clean change history. After merge, the work entered main through a traceable path instead of appearing as an unreviewed file.

The release tag closed the loop. It marked the card as shipped and gave the finished artifact a stable version.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/ee3aae6a-d0f4-444e-8c8f-6b5ee9efe331_p8h8bmp4)

### How the PR closed both issues automatically

The pull request closed both issues automatically because the PR linked the work to the issue tracker through the closing keywords. When the PR merged, GitHub moved the linked issues to completion.

That success should be documented in the README or After-Action Review as proof that the delivery loop worked. The writeup should state that the issues were opened, linked to the PR, closed by merge, and included in the tagged release.

This matters because the repository now proves more than the card itself. It proves that issue planning, branch work, pull request merge, and release tagging all connected.

### What the board proves about planned-to-done workflow

The board showed both issues in the Done column. That proved the workflow moved planned work into completed work through the GitHub process.

The movement was not just a manual status claim. It came from the pull request linkage between the implementation and the issue tracker.

That gave the build a clean planned-to-done trail. The board, PR, merge, and release all pointed to the same shipped work.

## Reflections and Takeaways

### Key tools and concepts from the project

The key tools I used included the GitHub CLI for repository work, Git for version control, VS Code as the code editor, and AI for the first documentation draft.

The main concepts I learned included using an unhedged honest-limit line, using a rubric as a quality gate, and moving work through a repeatable loop from issue creation to tagged release.

The larger lesson was that professional delivery is a system. The artifact matters, but the delivery trail is what proves the work was planned, checked, merged, and shipped.

### Time and challenge

This build took me approximately 60 minutes. That time covered tool setup, GitHub authentication, org verification, decision records, repository setup, AI drafting, rubric scoring, PR workflow, issue closure, and release tagging.

The hardest part was keeping the honest-limit line direct while still meeting the strict 3/3 rubric. The temptation was to soften the limitation, but the standard required a clear fact.

That challenge mattered because honest limits are part of technical precision. A card that hides its limits is weaker than a card that states them cleanly.

### What comes next

I completed this build to master the full GitHub delivery workflow. The process covered issue creation, board tracking, branch-based development, pull request merge, automatic issue closure, and tagged release.

The next skill I want to build is automated testing. Adding tests would make the delivery pipeline stronger by checking quality before merge instead of relying only on manual review.
