## Proving the Rules Work: Test Results and Alert Logic

### Why unit tests make the arithmetic a proof, not a claim

I built synthetic promtool tests to verify that the alert rules fire at the expected time and severity. The tests feed controlled counter data into the generated Prometheus rules, which lets me compare each result with the burn-rate thresholds I derived by hand. This turns the arithmetic into behavior that can be repeated and inspected.

A written formula only states what the rules should do. The unit tests check what they do when the input represents a known outage or slow leak. If an alert fires too early, too late, or at the wrong severity, the result exposes a difference between the derivation and the rule logic. Passing tests show that the synthetic conditions crossed the intended thresholds and produced the expected page or ticket response.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/0f9d4295-ec4d-4d06-953b-b081207acfd3_sy1ltbs8)

### What the two scenarios prove about burn rate and severity

The two scenarios show that alert severity follows the rate of budget consumption, not the simple presence of an error. A 10% outage creates a burn rate of 100. At that rate, the error budget is being consumed within hours, so the rules produce both a page and a ticket at the 1-hour evaluation point. Waiting until morning would allow too much of the budget to disappear.

The 0.2% leak creates a burn rate of 2. It produces a ticket at 6 hours but does not page anyone. That burn develops over weeks rather than hours, so the two-person roster can respond during working time. The tests prove that the rules distinguish urgent budget loss from a slower condition that still needs attention but does not justify waking someone overnight.

## Generating Alert Rules from a Single SLO Spec

### From SLI definition to generated MWMB rules

I wrote a Sloth specification for the 99.9% availability target and used it to generate the multi-window, multi-burn-rate alert rules. The specification provides one controlled definition for the SLI, objective, and alert settings instead of requiring the recording and alert rules to be written separately by hand.

The generated output established a baseline that I could compare with my manual calculations. This comparison mattered because generated rules are only trustworthy when I can explain how their thresholds connect to the error budget. I checked the burn rates and long/short windows against the values derived from the SRE Workbook method. The result connected the 99.9% target, its 0.001 error budget, the generated Prometheus rules, and the later promtool tests through one traceable source.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/0f9d4295-ec4d-4d06-953b-b081207acfd3_7v8dzuf4)

### Hand-deriving the four burn-rate thresholds

I derived each burn-rate threshold with the formula budget_share * 720 / window. The four results were 14.4, 6, 3, and 1. I then compared those values and the eight associated long/short windows with the MWMB rules generated by Sloth.

All twelve values matched. None of the four burn rates or eight windows contradicted the manual derivation. This showed that the generator followed the Workbook arithmetic rather than applying an unexplained constant.

The match also tied the page-versus-ticket behavior to the stated 99.9% availability target and its 0.001 error budget. If those values had differed, the alert rules could still have looked valid while acting on the wrong SLO assumptions. Hand calculation provided an independent check of the generated configuration.

## Why This Project Exists: Roster Math and the Error Budget

### Why a two-person roster makes the arithmetic non-optional

I built this system because a two-person on-call roster has little capacity for unnecessary alerts. Every overnight page interrupts one of only two people, so the alert must represent a condition that cannot safely wait. Burn-rate arithmetic provides a defensible way to separate that condition from slower budget loss.

The decision cannot depend on whether an error exists because every service produces some errors. The useful question is how quickly the current rate will consume the allowed error budget. A fast burn can break the availability promise before the next working day, while a slow burn can be investigated through a ticket.

Deriving the thresholds by hand lets me explain why an alert pages, how long the budget would last, and what trade-off the roster is making between response speed and alert fatigue.

## Setting Up the Toolchain

### What this step establishes

I initialized the repository and downloaded the Sloth and promtool binaries needed for the build. Keeping the toolchain with the repository created a version-controlled environment for generating SLO rules and running repeatable validation tests. It also recorded which tool versions produced the output.

Sloth converts the SLO specification into Prometheus recording and alert rules. promtool evaluates those rules against synthetic time-series data. Together, they connect the written objective to executable rule behavior.

This setup reduced dependence on undocumented global software. A reviewer can identify the required binaries, reproduce the generated files, and rerun the same tests from the repository. The environment therefore supports both the arithmetic work and the evidence used to check it.

### The starter folder and why each file is there

fetch.sh and fetch.ps1 download and verify Sloth v0.16.0 and the Prometheus 3.13.0 promtool binary on macOS/Linux or Windows. These scripts make the required versions explicit and provide equivalent setup paths for the supported operating systems.

reference-table.md contains the SRE Workbook Chapter 5 burn-rate table. worked-example.md records the 14.4 derivation. These files provide the reference math used to check the generator output instead of accepting its thresholds without explanation.

series-outage.txt and series-slowleak.txt define the promtool input series. The first models a 10% outage with a burn rate of 100. The second models a 0.2% leak with a burn rate of 2. Each file gives the tests a known condition with an expected response.

### Verified tool versions

## Designing the SLI and Arguing Every Denominator

### Why the design precedes the build

I designed three candidate Service Level Indicators and wrote three Architecture Decision Records before implementing the automated rules. This forced me to define what counted as a good event, what belonged in the total population, and why each denominator represented the service promise.

The denominator controls the meaning of an SLI. If it excludes difficult requests or includes failed requests in the wrong way, the ratio can look healthy while users are experiencing an outage. Writing the candidates and decisions first made those assumptions visible before Sloth generated any rules.

The ADRs preserved the reasoning behind the selected SLI and the rejected alternatives. That record makes later review easier because the team can inspect the original trade-offs instead of inferring them from PromQL after deployment.

### Rejecting a candidate SLI in writing

I rejected Candidate B, latency under 300ms, because its total_query still counted 5xx responses as valid latency events. Failed requests were not part of the population intended for successful latency measurement. Treating them as normal timing samples changed what the SLI claimed to measure.

The good-event query created a second problem. A fast 500 response could fall within le="0.3" and appear as a good event. During an outage, quick failures could raise the ratio even though the service was not completing requests successfully.

I also rejected Candidate C because removing 499 responses reduced the total population during load. That exclusion could make the denominator shrink when traffic conditions became difficult. Writing both rejections preserved why the candidate formulas were unsafe rather than only recording the final choice.

## Secret Mission: Teaching Burn Rate and Scoring the AI

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/0f9d4295-ec4d-4d06-953b-b081207acfd3_fzibnlmf)

### Explaining fast burns and slow burns to someone who has never carried a pager

A page means someone must respond now, even if it wakes them overnight. A ticket records a problem that can wait until morning. The difference depends on how quickly the service is spending its monthly error budget, not on whether the error rate is above zero.

A burn rate of 14.4 would consume the month's 43 minutes of allowed unavailability in about two days. Waiting through the night could put the service close to breaking its promise, so that condition deserves a page. A burn rate of 2 takes weeks to consume the same budget, so it can create a ticket instead.

This distinction protects a two-person roster from noise without hiding urgent failures. If every leak paged, the team could start ignoring alerts. If nothing paged, a fast burn could empty the budget before anyone responded.

## Reflections and Key Takeaways

### Tools and concepts from the project

I used the Sloth CLI to generate Service Level Objective rules and Prometheus promtool to test them against synthetic cases. Git tracked the source and generated changes, a local text editor supported the technical documentation, and an AI chat client helped me revise the explanations.

The main concepts were error budgets and multi-window, multi-burn-rate alerting. I learned how to derive burn-rate thresholds from the budget share and observation window, then compare those results with generated rules. I also learned to separate paging conditions from ticket-only alerts based on the speed of budget loss.

The ADRs showed why alert thresholds need recorded reasoning. During an on-call rotation, the team should be able to explain why an alert exists and why its severity matches the risk.

### Time and challenges

This build took approximately 65 minutes. The hardest part was deriving the burn-rate thresholds and reconciling the manual calculations with the Sloth-generated output. The work required a precise understanding of how the budget share, 720-hour period, and long/short windows combine within MWMB alerting.

The comparison could not stop at checking one headline number. I needed to verify the four burn rates, the eight windows, and the resulting page-versus-ticket behavior. A mismatch in any of those values could change when the roster is interrupted.

Completing the derivation gave me a stronger basis for trusting the rules. I could trace each threshold back to the 99.9% objective and explain the result without treating generated configuration as self-validating.

I completed this build to master the arithmetic behind SRE error budgets. I derived the burn-rate thresholds from first principles, generated the corresponding rules with Sloth, and validated their behavior with promtool under controlled MWMB scenarios.

The work connected the availability target to the operational decision of when to page and when to create a ticket. It also showed why synthetic tests prove rule behavior but do not replace production evidence.

My next step is to apply these concepts to live infrastructure by building automated SLO dashboards and observability pipelines for distributed systems. That work would add real metrics, deployed rule evaluation, and alert delivery to the foundation established here.
